# Idea: Apply Feedback to Result File

> Status: idea:captured
> Created: 2025-01-15
> Source: `TODO.md` (элемент «Применение пользовательских правок к итоговому файлу»), `docs/agents/03-backend.md`

## Raw Idea

После очистки документа пользователь получает результат с плейсхолдерами. В review-секции UI он видит все замены и может править: например, вернуть `<PRIVATE_PERSON1>` обратно в `Иванов` (откатить замену) или, наоборот, заменить кусок текста на плейсхолдер вручную. Кнопка «Сохранить правки в файл» должна применить эти правки к `result.{md|docx}` с **сохранением сквозной нумерации плейсхолдеров**.

## Problem Space

- Без этой фичи review-секция — «мёртвая»: пользователь видит замены, но не может их применить к итоговому файлу.
- Правки в review ссылаются на **исходный** текст (по сущностям из privacy-filter), а не на координаты в **очищенном** файле. Прямое применение требует трансляции offsets.
- Нумерация плейсхолдеров **сквозная по документу** (P-005) — любая вставка/удаление плейсхолдера должна сдвигать счётчики у последующих того же типа, иначе нарушатся ссылки.

## Target Users

- **Автор документа** (юр/аналитик/журналист/разработчик) — финализирует очищенный документ перед загрузкой в LLM.
- **Редактор** — проверяет качество замен, правит ложные срабатывания, дополняет пропуски.

## Current Alternatives

- Скачать очищенный файл, открыть в редакторе, править руками → теряются плейсхолдеры (пользователь не знает, какие `n` заняты, легко сделать коллизию).
- Не использовать review → получать менее качественную очистку (модель может ошибаться).

## Desired Outcome

- Кнопка «Сохранить правки в файл» транслирует правки из review в координаты очищенного файла.
- Файл `result.{md|docx}` обновляется на месте (или пересоздаётся) с применёнными правками.
- Сквозная нумерация плейсхолдеров сохраняется: `<PRIVATE_PERSON1>` остаётся `<PRIVATE_PERSON1>` и т.д.
- Источник истины — единый эндпоинт `POST /api/v1/documents/{id}/apply-feedback`.

## Possible Directions

### Direction A: Server-side offset translation

- **Description:** Backend хранит `replacement_map` (не путать с reverse map; это **forward** map «исходный span → плейсхолдер») **временно** на время сессии обработки, удаляется при apply. Эндпоинт принимает список правок `{ original_span, new_text }` и транслирует их в координаты очищенного файла.
- **Pros:** Консистентная трансляция; UI не нужно знать про offsets в очищенном файле.
- **Cons:** Требует хранения `replacement_map` — **конфликтует с P-003** (No Reverse Map), если не разделить чётко: forward map для трансляции правок ≠ reverse map для восстановления PII. **Требует явного обоснования.**
- **Risks:** Если forward map утечёт — он раскрывает «что на что заменили», что эквивалентно половине reverse map. Нужно удалять сразу после apply и не логировать.

### Direction B: Client-side offset translation

- **Description:** UI хранит offset-карту во время сессии (в памяти браузера), транслирует правки локально, отправляет на сервер уже **готовый** новый текст/файл.
- **Pros:** Сервер не хранит карту вообще; минимум PII-поверхности.
- **Cons:** UI сложнее; offset-карта живёт долго (пока пользователь думает) → может утечь через XSS/расширения.
- **Risks:** Безопасность браузерной памяти (PII в JS-объектах).

### Direction C: Hybrid — server-side, но без хранения карты

- **Description:** При apply UI отправляет **полный diff** (исходный текст + новый текст); сервер перепарсит `result.txt` (если есть кэшированный извлечённый текст) и применяет diff. Кэш `result.txt` живёт только до apply/fail и не пишется на диск.
- **Pros:** Карта не хранится даже временно; консистентно с P-003.
- **Cons:** Требует перепарсинга; UI должен отдавать diff (что усложняет клиент).
- **Risks:** Diff может быть неоднозначным; нужен аккуратный алгоритм.

## Open Questions

- **Q-001 (направление):** A, B или C? По `TODO.md` выбрано A (эндпоинт `apply-feedback` с трансляцией offsets). Подтвердить.
- **Q-002 (хранение forward map):** хранить ли forward map в `job.json`/отдельном файле? Если да — **нарушает ли это P-003**?
- **Q-003 (UI-поток):** одна кнопка «Применить всё» или каждая правка применяется отдельно? UX-решение.
- **Q-004 (для .docx):** как применить правки, если `result.docx` собран без runs/форматирования? — Перепарсить и пересобрать, или хранить промежуточный текст?
- **Q-005 (идемпотентность):** что происходит при повторном apply? Возвращать 409, если уже применено? Или молча перезаписывать?
