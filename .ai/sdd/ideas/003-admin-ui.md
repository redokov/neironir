## Raw Idea

Веб-интерфейс для администратора системы. Позволяет:
- Видеть счётчик обработанных документов (всего / за период).
- Просматривать feedback по каждому документу (какие PII найдены, какие правки внёс пользователь).
- Запускать дообучение `opf train` на накопленных аннотациях.
- Видеть статус дообучения (прогресс, текущая эпоха, loss, ETA).
- Утверждать/отклонять предложенные правила (через UI + API).

## Problem Space

- Без админки: оператор не знает, сколько документов обработано, какие правки пользователи делают, как модель учится.
- Запуск `opf train` вручную через CLI — требует доступа к серверу; неудобно для регулярных переобучений.
- Аннотации (правки пользователей) — ценный сигнал для дообучения, но без админки они «лежат мёртвым грузом».
- Предложенные правила (от модели или от эвристик) требуют ручного одобрения — без UI это сценарий «открыть файл, поредактировать, перезапустить».

## Target Users

- **Администратор системы** (один человек; позже — команда): обслуживает `neironir`, дообучает модель, контролирует качество.
- Не конечный пользователь (тот, кто загружает документы) — для него остаётся основной UI.

## Current Alternatives

- CLI-only: `opf train` запускать руками, логи смотреть в файлах, счётчики — `wc -l storage/jobs/*/job.json`.
- Внешние инструменты (Grafana + Prometheus) — избыточно для MVP.
- Ручное редактирование файлов с правилами — небезопасно, неаудитируемо.

## Desired Outcome

- Защищённый (в MVP — single-user, но в коде — подготовленный к auth) раздел `/admin`.
- Дашборд: счётчики документов (total / period), список последних обработанных.
- Страница документа: feedback (правки пользователя), diff, метаданные.
- Кнопка «Запустить дообучение» → backend стартует `opf train` (subprocess), polling статуса.
- Страница дообучения: прогресс, эпоха, loss, ETA; возможность остановить.
- Управление правилами: список предложенных правил, кнопки «Одобрить» / «Отклонить» (с логированием решения).
- Audit log всех админ-действий.

## Possible Directions

### Direction A: Vanilla SPA внутри существующего frontend (как `admin.html`)

- **Description:** Расширить `frontend/` — добавить `admin.html`, `admin.js`, `admin.css`. Переиспользовать утилиты (polling, fetch, UI-компоненты).
- **Pros:** Минимум новых зависимостей; единый стек; простая интеграция с backend.
- **Cons:** Vanilla JS может стать громоздким для админ-таблиц/фильтров.
- **Risks:** Смешение user-facing и admin UI в одном репо — но это OK для MVP.

### Direction B: Отдельный admin-сервис

- **Description:** Другой порт, другой стек (например, React), отдельный бэкенд.
- **Pros:** Изоляция, можно выбирать стек независимо.
- **Cons:** Усложнение развёртывания (ещё один процесс), дублирование кода.
- **Risks:** Overhead для MVP.

### Direction C: Использовать существующий BI/observability-стек

- **Description:** Grafana + Prometheus + alertmanager.
- **Pros:** Масштабируется, отраслевой стандарт.
- **Cons:** Требует инфраструктуры, которую MVP не предполагает; out of scope.
