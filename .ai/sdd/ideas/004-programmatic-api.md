# Idea: Programmatic (M2M) API

> Status: idea:captured
> Created: 2025-01-15
> Source: потребность внешних систем в программной анонимизации без UI; утверждённые решения пользователя (см. Decisions)

## Raw Idea

Внешние системы (скрипты, интеграции, другие сервисы) должны уметь использовать `neironir` программно: загрузить документ `.md`/`.docx` → анонимизировать → забрать результат. Сейчас единственный путь — UI-флоу (session cookie + CSRF), неудобный для машинной интеграции (нет login-form, нет cookie-jar-логики у простых клиентов).

## Problem Space

- Session-аутентификация ориентирована на браузер: внешнему клиенту нужно эмулировать form-login, хранить cookie, получать CSRF-токен — лишняя сложность для M2M.
- `curl`/CI-джобы/интеграционные скрипты хотят простой контракт: один статический токен в заголовке `Authorization`.
- Результат нужен в двух форматах: бинарный файл (download) и JSON с base64-контентом (для программной обработки без сохранения во временный файл).

## Target Users

- **Внешняя система / интеграционный сервис** — автоматическая анонимизация документов в пайплайне без участия человека.
- **Скрипты и CI** — программная очистка файлов перед отправкой в LLM.
- **Существующий UI-пользователь** — его флоу не должен измениться.

## Current Alternatives

- Эмуляция browser-флоу (login → cookies → CSRF) — хрупко и избыточно для M2M.
- Запуск `opf` CLI напрямую — дублирует конвертеры, пайплайн и нумерацию плейсхолдеров вне сервиса.

## Desired Outcome

- Аутентификация по статическому API-ключу: `Authorization: Bearer <token>`, список ключей в конфиге/`.env`.
- Расширение существующих эндпоинтов `/api/v1/documents` (не отдельный префикс): upload → 202 + job_id → polling → результат.
- Два способа выдачи результата: бинарный download (как сейчас) и JSON с base64-контентом.
- Session-флоу (UI) продолжает работать без изменений.
- E2E-тесты на реальной развёрнутой модели (subprocess-режим), не только mock.

## Possible Directions

### Direction A: Расширение существующих эндпоинтов `/api/v1/documents`

- **Description:** те же URL; аутентификация принимает либо session-cookie, либо `Authorization: Bearer` API-ключ. JSON-формат результата — дополнительный эндпоинт/параметр рядом с download.
- **Pros:** один контракт, минимум новой поверхности; UI и M2M используют одни URL.
- **Cons:** логика «или session, или ключ» в каждом защищённом эндпоинте — нужно аккуратно описать конфликт-правила.
- **Risks:** непреднамеренное открытие admin-эндпоинтов по API-ключу — требует явного списка защищённых ресурсов.

### Direction B: Отдельный префикс `/api/v1/machine` или `/api/v2`

- **Description:** параллельный набор эндпоинтов только для M2M.
- **Pros:** чистая изоляция политик.
- **Cons:** дублирование контракта, два места поддержки, расхождение со временем.

### Direction C: OAuth2 client-credentials flow

- **Description:** полноценный token-endpoint, выдача короткоживущих токенов.
- **Cons:** for one local service — overengineering; статических ключей достаточно.

## Open Questions

- **Q-001 (ревокация/ротация ключей):** нужны ли per-key метаданные (имя, владелец, дата) и аудит использования, или достаточно «плоский список строк в .env»?
- **Q-002 (CSRF для M2M):** требуется ли CSRF-токен для API-ключей при unsafe-методах (POST upload)? (Для Bearer-аутентификации CSRF обычно не нужен — нет cookie.)
- **Q-003 (доступ к review/feedback-эндпоинтам):** нужны ли M2M-клиентам annotations/feedback/apply-feedback, или только upload → poll → download?
- **Q-004 (доступ к admin/rules):** распространяется ли API-ключ на admin-эндпоинты? (Рекомендация: нет.)
