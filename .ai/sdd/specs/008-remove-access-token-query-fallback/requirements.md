# Feature: Remove `?access_token=` query fallback

> Status: Approved
> Source: `.ai/sdd/ideas/005-remove-access-token-query-fallback.md`
> Last Updated: 2026-11-09

## Overview

Убрать одноразовый job access token из URL: скачивание из веб-интерфейса
переводится на `fetch()` с заголовком `X-Job-Token`, а запасная ветка
`?access_token=` на сервере удаляется. Токен больше не оседает в истории
браузера, access-логах сервера и заголовке Referer.

## Business Context

- **Problem:** скачивание идёт по `<a href>` с токеном в query-параметре
  `?access_token=...`. Job-токен попадает в URL, историю браузера, журналы
  сервера и referrer. Digest-only модель (spec 007 T3) защищает хранилище,
  но сам токен протекает на транспортном уровне.
- **Users:** локальный пользователь веб-интерфейса; M2M-клиенты не затронуты
  (они уже работают через заголовок).
- **Value:** токен задачи не появляется в URL нигде и никогда; поверхность
  утечки токена сокращается до заголовков HTTP.
- **Success signal:** скачивание из UI работает; `GET /download?access_token=…`
  возвращает 404; все regression-гейты зелёные.

## Goals

- Скачивание из веб-интерфейса — запросом из сценария (fetch) с заголовком
  `X-Job-Token`; файл сохраняется через `Blob`/`URL.createObjectURL`.
- Удалить ветку query-параметра `access_token` в `verify_job_access`.
- Зафиксировать ломающее изменение: старые открытые ссылки со встроенным
  токеном перестают работать (приемлемо, версия до 1.0).

## Non-Goals / Out of Scope

- Короткоживущий одноразовый download-ticket для navigation-скачивания
  (опция из идеи 005 — не требуется, fetch-схема закрывает потребность).
- Изменение контрактов M2M API (`Authorization: Bearer` + `X-Job-Token`).
- Персистентный реестр отзывов jti (отдельная идея 006).
- Обратная совместимость старых ссылок с токеном в URL.

## User Stories

- **US-1.** Как пользователь веб-интерфейса, я хочу скачивать очищенный
  файл по кнопке, чтобы токен задачи не попадал в историю моего браузера.
- **US-2.** Как оператор сервера, я хочу, чтобы job-токены никогда не
  появлялись в access-логах, чтобы скомпрометированные логи не давали
  доступ к задачам.

## Functional Requirements

- **FR-001 (EARS):** WHEN сервер получает job-scoped запрос с токеном в
  query-параметре `access_token`, THE SYSTEM SHALL отвечать тем же
  неразличимым `404 job_not_found`, что и при отсутствии токена.
- **FR-002 (EARS):** WHEN пользователь нажимает «Скачать очищенный файл»,
  THE WEB CLIENT SHALL выполнять `fetch` c заголовком `X-Job-Token` и
  сохранять ответ как файл через Blob, БЕЗ размещения токена в URL.
- **FR-003 (EARS):** WHILE задача открыта в UI, THE WEB CLIENT SHALL
  использовать токен, уже сохранённый в состоянии фронтенда после загрузки
  (spec 007 T3), БЕЗ повторного запроса.

## NFRs

- **NFR-001:** поведение сервера для неверного/отсутствующего токена и
  query-токена остаётся неразличимым (единый 404, без раскрытия
  существования UUID).
- **NFR-002:** без новых зависимостей фронтенда (vanilla JS).
- **NFR-003:** регресс-гейты (ruff/mypy/pytest/node) остаются зелёными.

## Boundaries / Edge Cases

- Legacy-задачи без digest: без изменений — 404 для non-admin (spec 007).
- admin-сессия: без изменений — явный bypass проверки токена.
- Обработчик клика по ссылке обязан не открывать URL напрямую
  (`preventDefault`), иначе браузер сделает navigation без заголовка.
- Ошибка скачивания (сеть/404) показывается пользователю, состояние UI
  не ломается.

## Breaking Change

Старые открытые ссылки вида `/download?access_token=...` перестают
работать (404). Приемлемо: проект pre-1.0, токен выдаётся на задачу и
носит краткоживенный характер.
