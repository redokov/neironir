# Decisions: Apply Feedback to Result File (FR-1)

## D-001 — Удалить три кнопки

**Date:** 2025-01-15  
**Status:** Accepted  
**Context:** Пользователь сообщил, что кнопки «Всё верно», «Отправить правки», «Пропустить» бессмысленны в текущем UX.  
**Decision:** Удалить кнопки + связанные DOM-элементы + JS-обработчики + функции (`confirmAll`, `submitFeedback`, `postFeedback`).  
**Reason:** 
- «Всё верно» / «Отправить правки» шлют `POST /feedback` — пишут только `feedback.json` для обучения, **не обновляют** `result.md`. После нажатия UI показывает «Спасибо! Ваши правки сохранены» — пользователь думает, что файл обновлён, но это не так.
- «Пропустить» закрывает секцию без действий — лишняя кнопка.
- «Сохранить правки в файл» (`POST /apply-feedback`) — единственная кнопка, которая реально перезаписывает файл. Оставляем её.
**Consequences:** Пользователь видит одну кнопку — не путается. API `POST /feedback` остаётся в бэкенде (для админки / дообучения), но в UI не вызывается.  
**Alternatives considered:**
- Переименовать «Всё верно» в «Подтвердить (без правок)» и оставить — отвергнуто, дублирует apply.
- Скрыть кнопки через `hidden`, не удалять — отвергнуто, мёртвый код.

## D-002 — Re-render preview из локально модифицированного reviewData

**Date:** 2025-01-15  
**Status:** Accepted  
**Context:** Сценарий B (recon 2025-01-15) — после успешного `POST /apply-feedback` UI вызывает `GET /annotations`, получает **старые** данные (аннотации не обновляются apply'ом), и preview показывает прежнюю картину. Пользователь интерпретирует это как «правки не сохранились».  
**Decision:** После успешного apply модифицировать `reviewData` локально на основе отправленных actions и вызвать `renderPreview()`.  
**Reason:**
- Бэкенд не отдаёт новое состояние preview (D-003 — не трогаем бэкенд).
- `GET /annotations` возвращает старые данные — это known-issue.
- Логика нумерации плейсхолдеров уже есть на клиенте через `PlaceholderCounter` (если импортируется) или дублируется минимально.
**Consequences:** 
- preview совпадает с `result.md` после apply.
- Дублирование логики нумерации — риск расхождения. Митигация: статтест.
**Alternatives considered:**
- Перезагрузить `result.md` через `GET /download` и распарсить — отвергнуто, сложно для docx, и `result.md` не совпадает с `extracted_text` (это другой артефакт).
- Обновить `annotations.json` на бэкенде в `apply-feedback` — отвергнуто, D-003 (не трогаем бэкенд в этом фиксе; может быть отдельной задачей позже).

## D-003 — Не трогать бэкенд

**Date:** 2025-01-15  
**Status:** Accepted  
**Context:** recon 2025-01-15 показал, что `POST /apply-feedback` корректно перезаписывает `result.md`. Баг — на стороне UI.  
**Decision:** Изменения только в frontend. Бэкенд не трогаем.  
**Reason:** Минимизация поверхности изменений; `apply-feedback` уже работает правильно; изменения в API-контракте = breaking change для админки и любых интеграций.  
**Consequences:** Бэкенд остаётся стабильным; UI-фикс решает наблюдаемый баг.  
**Alternatives considered:**
- Добавить в `ApplyFeedbackResponse` поле `updated_annotations` — отвергнуто, расширение API, не нужно для фикса.
- Обновить `annotations.json` после apply — отвергнуто, мутация артефакта, не нужна.

## D-004 — Удалить `postFeedback` полностью

**Date:** 2025-01-15  
**Status:** Accepted (refinement of TD-002)  
**Context:** После удаления `confirmAll` и `submitFeedback` функция `postFeedback` остаётся без вызывающих. Нужно решить, оставить ли её.  
**Decision:** Удалить `postFeedback` полностью.  
**Reason:** 
- `admin.js` использует свой `fetch` (проверено grep'ом) — не вызывает `postFeedback` из `app.js`.
- Мёртвый код = лишний риск случайного вызова + шум в diff'ах.
**Consequences:** Меньше кода; при необходимости легко восстановить из git.  
**Alternatives considered:**
- Оставить как утилиту для будущего — отвергнуто, YAGNI.
