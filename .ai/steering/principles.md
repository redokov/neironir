# Project Principles

> Status: Active
> Last Updated: 2025-01-15

## Purpose

Эти принципы определяют нетехнические и кросс-функциональные правила, которым следуют PRD, SPEC, TASKS, EXEC и REVIEW в проекте `neironir`. Они не заменяют конкретные требования, а помогают выбирать между равноценными вариантами и поддерживать единую философию продукта.

## How to Use These Principles

- **`MUST`** — ненарушимое правило, если пользователь явно не изменил его.
- **`SHOULD`** — сильное правило по умолчанию; исключения требуют обоснования.
- **`MAY`** — допустимый вариант, не обязательный.
- Если принципы конфликтуют с одобренными SDD-артефактами — остановиться и уточнить, какой источник править.

## Principles

### P-001: Privacy First

**Level:** MUST  
**Rule:** Никакая функциональность не должна сохранять, логировать или передавать наружу данные, которые позволяют восстановить исходные PII.  
**Reason:** Это основная ценность продукта; компрометация этого принципа уничтожает смысл сервиса.  
**Applies to:** PRD, SPEC, TASKS, EXEC, REVIEW

### P-002: Local-Only by Default

**Level:** MUST  
**Rule:** PII никогда не покидают машину пользователя. Никакие облачные API, телеметрия, third-party SaaS для самого процесса очистки.  
**Reason:** Локальность — единственный способ гарантировать приватность (P-001) технически, а не только политически.  
**Applies to:** PRD, SPEC, TASKS, EXEC, REVIEW

### P-003: No Reverse Map

**Level:** MUST  
**Rule:** Карта замен (исходный текст → плейсхолдер) **не хранится нигде**: ни в БД, ни в логах, ни в файлах на диске, ни в памяти дольше, чем нужно для одной операции.  
**Reason:** Даже временное хранение карты — это риск восстановления PII при компрометации.  
**Applies to:** PRD, SPEC, TASKS, EXEC, REVIEW

### P-004: 8 Types Is a Closed Set

**Level:** MUST  
**Rule:** Набор типов PII фиксирован: `private_person`, `private_address`, `private_email`, `private_phone`, `private_date`, `private_url`, `account_number`, `secret`. Расширение — только через явное требование и обновление `EntityType`.  
**Reason:** Стабильность имён плейсхолдеров — контракт между сервисом и пользователем; менять «по ходу» — ломать документы.  
**Applies to:** PRD, SPEC, TASKS

### P-005: Per-Document Numbering

**Level:** MUST  
**Rule:** Нумерация плейсхолдеров (`<PRIVATE_PERSON1>`, `<PRIVATE_PERSON2>`, …) — **сквозная в пределах одного документа** и **сбрасывается в 1 для нового документа**.  
**Reason:** Сквозная нумерация упрощает ссылки в review/feedback; сброс по документу — естественная граница задачи.  
**Applies to:** SPEC, TASKS, EXEC

### P-006: Stable Placeholder Format

**Level:** MUST  
**Rule:** Формат плейсхолдера — `<TYPE_N>` в `UPPER_SNAKE_CASE`, `<` и `>` обязательны. Изменение формата — breaking change, требует миграционного периода.  
**Reason:** Пользователи (и скрипты) могут полагаться на формат при дальнейшей обработке очищенных документов.  
**Applies to:** SPEC, TASKS

### P-007: Mock and Real Are First-Class

**Level:** MUST  
**Rule:** И `mock` (regex-эвристика), и `subprocess` (реальный `opf`) — поддерживаемые режимы. `mock` — не костыль для разработчика, а полноценный режим для CI и offline-использования.  
**Reason:** Без `mock` невозможен CI; без `subprocess` — production; оба должны быть протестированы.  
**Applies to:** SPEC, TASKS, EXEC, REVIEW

### P-008: Test the Real Model Before Release

**Level:** MUST  
**Rule:** Перед релиз-тегом обязателен `make test-real` (real_model тесты) — без него релиз не считается валидным.  
**Reason:** Mock не покрывает реальную интеграцию с моделью; регрессии в pipeline видны только с реальным `opf`.  
**Applies to:** EXEC, REVIEW

### P-009: Coverage Gate 70%

**Level:** MUST  
**Rule:** Coverage в CI — не ниже 70%. Снижение — через явное обоснование в PR.  
**Reason:** Поддерживать качество кода; ниже — слишком много «серых» зон в приватном коде.  
**Applies to:** EXEC, REVIEW

### P-010: One User, One Process

**Level:** SHOULD  
**Rule:** Архитектура MVP — один пользователь, один процесс Uvicorn, фоновые задачи в нём же. Масштабирование, авторизация, очереди — за рамками MVP.  
**Reason:** Минимизация поверхности атаки и сложности для MVP; расширение — отдельная фаза с собственным PRD.  
**Applies to:** PRD, SPEC

### P-011: Native Format In, Native Format Out

**Level:** MUST  
**Rule:** Входной формат определяет выходной: `.md` → `.md`, `.docx` → `.docx` (опционально `.docx → .md` — отдельный чекбокс).  
**Reason:** Пользователь ожидает получить документ той же формы, что загрузил; конвертация — явный и опциональный шаг.  
**Applies to:** PRD, SPEC, TASKS

### P-012: Format Limitations Are Documented

**Level:** MUST  
**Rule:** Все ограничения конвертеров (например, `.docx` сохраняет только параграфы — без runs, таблиц, списков, изображений) явно задокументированы в `docs/architecture.md` и/или в UI.  
**Reason:** Пользователь не должен удивляться потере форматирования.  
**Applies to:** PRD, SPEC, EXEC

### P-013: Spec Before Code

**Level:** MUST  
**Rule:** Новая фича проходит через `sdd-idea → sdd-prd → sdd-spec → sdd-tasks` с явным одобрением перед написанием кода. Прямая реализация без спецификации — только для тривиальных bugfix/typing/cosmetic.  
**Reason:** SDD-процесс защищает от переделок и потери контекста; для проекта, затрагивающего приватность, это особенно важно.  
**Applies to:** EXEC

### P-014: Security and Privacy Outrank UX

**Level:** MUST  
**Rule:** Если есть конфликт между удобством и приватной/безопасностью — приватная/безопасная опция выбирается по умолчанию.  
**Reason:** Продукт продаёт приватность; любая утечка перечёркивает всё остальное.  
**Applies to:** PRD, SPEC, EXEC

### P-015: Configuration via `.env` and `pydantic-settings`

**Level:** MUST  
**Rule:** Все настройки читаются из переменных окружения через `pydantic-settings`. Прямые хардкоды в коде — только для дефолтов в `config.py`.  
**Reason:** Воспроизводимость, тестируемость, безопасность (`.env` в `.gitignore`).  
**Applies to:** SPEC, TASKS, EXEC

## Decision Rules

1. **P-001, P-002, P-003** — ненарушимы; конфликт с ними = блок.
2. Если два `SHOULD` конфликтуют — обсудить с пользователем и зафиксировать в `decisions.md`.
3. Простое решение предпочтительнее сложного, если оба проходят требования.
4. Если trade-off непонятен — остановиться и спросить.
5. Изменение `MUST`-принципа — только через явное одобрение пользователя и обновление этого файла.

## Review Expectations

- [ ] Каждое требование проверяется на соответствие `P-001…P-006`, `P-011`, `P-012`.
- [ ] Дизайн обосновывает любые отклонения от `SHOULD`-принципов.
- [ ] Таски включают верификацию для principle-sensitive work (особенно P-001, P-002, P-003, P-007, P-008).
- [ ] Review проверяет, что `make test-real` пройден перед релизом (P-008).
- [ ] Coverage ≥ 70% подтверждён (P-009).

## Change Policy

- Изменение `MUST`-принципа требует явного одобрения пользователя.
- Изменённые принципы не переписывают молча одобренные SDD-артефакты — нужно явное обновление требований/дизайна/тасок.
- История изменений принципов фиксируется в этом файле (через PR с описанием).
